Ten stages,
five gates

Work decomposes into Epics, Features and Stories. Nothing is implemented until its change folder exists, validates, and a human has approved it — that is the one hard gate. After it, scenarios are worked one at a time, red → green, until every scenario in the delta has a passing test of the same name. The change is archived as the last commit on the same branch, so one PR carries the spec, the code, and the merge into the source of truth.

The line, end to end

Every gate is a place where work stops until a named condition holds. Colour says who clears it: a human, or the machine.

Three levels, three anchors

The repo owns content; GitHub owns state and order. Nothing is written down twice — an issue body holds a sentence of intent, a link, and gate checkboxes, never requirements.

One scenario at a time

A settled spec is a complete set of behaviours imagined before any code — which is exactly what the tdd skill calls horizontal slicing and names an anti-pattern. The resolution is consumption order: the spec is written up front, the tests are not.

One Story, one branch, one PR

The archive is the last commit on the same branch, not a follow-up PR. That is what lets a single PR carry the spec, the code and the merge into the source of truth.

What closes, and what never does

open has exactly one meaning at every level: there is outstanding work under this node. It has to — ADR-0012 dropped the project board, so open/closed is the primary state signal, and a signal carrying two meanings stops answering where is everything.

LevelClose whenReopen when
StoryIts PR merges — automatic, nothing to do.Never. New work is a new Story.
FeatureNo open Story under it, and none queued.A new Story is cut against that capability.
EpicEvery Feature under it is closed.Any child Feature reopens.

A Feature is not “forever” because its issue stays open. What lives forever is the spec. The issue tracks work against it, and reopening is free — which is what keeps one Feature issue matched to one capability spec instead of accumulating a second one every time the capability is revisited.

Read the children, not the parent’s rollup. sub_issues_summary is eventually consistent — it was observed still reading 0/1 immediately after the child closed, correcting moments later. Fine for a glance, wrong for a decision made in the same breath as the close. And a triaged bug carrying needs-triage with no issue type sits outside the hierarchy by design: it is inbox, not plan, and does not hold its Feature open.

What CI actually checks

Eight checks on every PR. Checks 2–6 are bespoke scripts in scripts/ — the most likely part of the system to rot.

01Validate everythingopenspec validate --all --strict --no-interactive
02Spec-diff containmentEvery file changed under openspec/specs/ belongs to a capability the archived delta names. On a chore/ branch the set must be empty. This is the check that makes the source of truth safe.
03Single-change ruleA story/ PR adds exactly one directory under changes/archive/ and leaves no active folder behind.staged — reports locally
04Scenario coverageEvery #### Scenario: in the delta has an acceptance test whose title matches it verbatim.staged — reports locally
05G4 approval recordedThe Story issue carries a comment beginning G4: approved. This is what turns “no implementation before G4” from a convention into a red build.
06Commit hygieneNo commit on the branch carries an attribution trailer or names a tool.
07Verifypnpm run verify — lint, typecheck, test.
08Archive completeopenspec validate --archived — every tasks.md checkbox in the newly archived change is ticked.

Why 3 and 4 are staged. Run locally on a Story still in flight they report rather than fail — the single-change rule reads “still active” until Stage 8, and coverage reports 2/4 covered — next: "<title>". Failing locally would demand every acceptance test at once, which is precisely the bulk transcription rule 3 forbids. In CI they bind, because a PR asserts the Story is finished.

When not to run any of this

chore/<slug>

The escape hatch

No behaviour change, no Story, no Feature, and it may not touch openspec/specs/ at all — check 2 requires an empty set. Tooling, dependency bumps, docs, CI. Without this lane a one-line bump would need an Epic and you would abandon the process within a month. If you reach for it to add behaviour, that is the process telling you to write a Story.

< 2 hours

The proportionality rule

The gates cost roughly 45–90 minutes of your own time per Story. A Story smaller than about two hours of work must not go through the full pipeline — batch it, or route it through chore/. One exception: a Story whose purpose is to exercise the pipeline itself, which must say so in its intent. Absent that sentence, a cold agent should push back on the assignment rather than proceed.

if it hurts

Cut in this order

Fold Stage 3 into Stage 4 · fold Stage 7 into Stage 8 · drop the Epic level · drop CI checks 3 and 4. Never cut G4 or CI check 2 — those two are the process; everything else is scaffolding around them. The retrospective scores this list against the first end-to-end Story: the order changed, the two never-cut items did not.
